## 二、全栈开发：先搞懂这些词

如果你刚接触 Web 全栈，下面是最小概念集。后面讲深知架构时会反复用到。

### 2.1 前端（Frontend）

用户能看到的页面：按钮、输入框、对话气泡、侧边栏等。

- **技术**：Next.js（基于 React）+ TypeScript  
- **在本项目里**：主要在 `apps/web/features/` 和 `apps/web/components/`  
- **职责**：展示 UI、收集用户输入、调用后端接口、处理流式回复（逐字显示）

### 2.2 后端（Backend）

用户看不到的服务：处理业务逻辑、调 AI、查论文库、存会话等。

- **技术（目标态）**：Python FastAPI（`apps/backend/`）  
- **技术（当前过渡）**：Next.js 的 Route Handlers（`/api/b/*`）也承担一部分 AI 逻辑  
- **职责**：鉴权校验、配额、调用 DeepSeek/百炼、读写数据库

### 2.3 BFF（Backend For Frontend，面向前端的中间层）

浏览器**不直接**访问 FastAPI 或数据库，而是先请求**同一个网站域名**下的 API 路径，再由 Next.js 转发或处理。

```text
浏览器  →  https://你的站点/api/...  →  Next.js（BFF）  →  FastAPI / 数据库 / 外部 API
```

好处：

- 登录 Cookie 留在 Next 层，不会泄漏给 Python  
- 前端只写 `/api/v1/...`，不用关心后端部署地址  
- 可以在 BFF 注入用户身份（如 `X-Shenzhi-User-Id`）

### 2.4 API 与 HTTP

前后端通过 **HTTP 请求** 通信，常见方法：

| 方法 | 典型用途 |
|------|----------|
| GET | 查询（配置、会话列表、拉流） |
| POST | 创建（新会话、发送消息、上传） |
| PATCH | 部分更新（重命名会话） |
| DELETE | 删除 |

响应常见格式：

- **JSON**：`{ "code": 0, "data": { ... } }`  
- **SSE（Server-Sent Events）**：AI 逐段推送文字，类似「打字机效果」

### 2.5 数据库（Database）

持久化存储：用户、会话、消息等。

| 用途 | 技术 | 位置 |
|------|------|------|
| 登录账号 | PostgreSQL | Better Auth（`DATABASE_URL`） |
| Chat 会话（过渡） | SQLite | B 模块 Prisma（`B_CHAT_DATABASE_URL`） |
| Chat 会话（目标） | PostgreSQL | 与 FastAPI 统一（阶段二推进） |

原则：**不要另起第二套数据库方案**（见工程规范）。

### 2.6 鉴权（Authentication，Auth）

确认「你是谁」：注册、登录、Session、退出。

- **本项目唯一 Auth 内核**：Better Auth（`apps/web/lib/auth/`）  
- **入口**：`/api/auth/*`  
- **Chat 侧**：Next BFF 读取登录态后，把 `userId` 传给业务后端

### 2.7 类型契约（TypeScript Types）

前后端约定「请求体 / 响应体长什么样」，避免联调时对不上字段。

- **单一来源**：`apps/web/types/ai-search.ts`  
- 改接口前先改类型，再改实现

### 2.8 环境变量（Environment Variables）

配置密钥和地址，**不写进 Git**。

| 变量示例 | 含义 | 能否暴露给浏览器 |
|----------|------|------------------|
| `DATABASE_URL` | Auth 数据库 | ❌ 仅服务端 |
| `DEEPSEEK_API_KEY` | 大模型密钥 | ❌ 仅服务端 |
| `BUSINESS_BACKEND_URL` | FastAPI 地址 | ❌ 仅服务端 |
| `NEXT_PUBLIC_AI_BACKEND_MODE` | A/B 后端模式 | ✅ 会打包进前端 |

带 `NEXT_PUBLIC_` 前缀的变量会被浏览器看到，**绝不能放密钥**。

## 三、深知项目的整体架构

### 3.1 仓库结构（Monorepo）

一个 Git 仓库里放多个应用：

```text
shenzhi/
├── apps/
│   ├── web/          # Next.js 前端 + BFF（主开发面）
│   └── backend/      # FastAPI 业务后端（Python）
├── docs/             # 产品、Auth、工程文档
├── AGENTS.md         # 仓库级 Agent/开发规范
└── scripts/          # 飞书同步等脚本
```

### 3.2 核心调用链（必须能画出来）

这是飞书阶段一的验收点之一：

```text
Next.js Page / Feature     ← 用户打开的页面（/、/agents/ask）
        ↓
     Client               ← 浏览器里运行的 React 组件 + hooks
        ↓
  Next.js BFF              ← /api/auth、/api/b、/api/v1
        ↓
  FastAPI API              ← apps/backend（模式 A / 论文检索）
        ↓
  Service / 外部 API       ← DeepSeek、百炼、论文库、Tavily 等
```

**两条 AI 路径（由环境变量切换）**：

| 模式 | 环境变量 | AI 对话走哪里 | 说明 |
|------|----------|---------------|------|
| **B（默认）** | `NEXT_PUBLIC_AI_BACKEND_MODE=B` | `/api/b/*` | Next 内实现，已接 DeepSeek 真流式 |
| **A** | `NEXT_PUBLIC_AI_BACKEND_MODE=A` | `/api/v1/*` → FastAPI | 目标架构；FastAPI 仍在完善 |

**论文检索**（首页 Alt+Enter、搜索页）：走 `/api/v1/search/explore` → FastAPI → 外部论文库。

### 3.3 主站页面与代码对应关系

| 用户访问的路由 | 主要代码位置 |
|----------------|--------------|
| `/` 首页 | `features/home/` + `features/agents/components/composer` |
| `/search` 搜索 | `features/search/` |
| `/agents/ask` 问 AI | `features/agents/ask/` + `lib/ask/use-ask-session.ts` |
| `/agents` Agent 页 | `features/agents/components/agent-chat.tsx` |
| `/agents/b` | `modules/ai-agent-b/`（遗留，待合并） |
| 登录弹窗 | `components/auth/` + `/api/auth/*` |

### 3.4 `apps/web` 目录职责（改代码前先对号入座）

| 目录 | 放什么 | 不要放什么 |
|------|--------|------------|
| `app/` | 路由薄入口（一行 import 页面） | 复杂业务逻辑 |
| `features/` | 各页面完整实现 | 第二套 Agent UI |
| `components/` | 布局、Auth、通用 UI | Agent 专用 Composer（应在 features） |
| `lib/` | API 封装、hooks、工具函数 | 页面 JSX |
| `types/` | 前后端契约 | 业务组件 |
| `modules/ai-agent-b/` | B 实验模块 | 新的公共组件（应上提到 lib） |

路径别名：

- `@/` → `apps/web/`  
- `@b/` → `apps/web/modules/ai-agent-b/`（逐步减少直接引用）

## 四、两条典型业务流程（建议亲手跟一遍）

### 4.1 用户登录

```text
1. 用户在页面点「登录」
2. 浏览器 → POST /api/auth/sign-in/...
3. Next.js Better Auth 校验邮箱/密码或 GitHub OAuth
4. 写入 PostgreSQL（user / session 表）
5. 浏览器收到 Session Cookie，后续请求自动带上
```

详细说明：`docs/auth/ARCHITECTURE.md`

### 4.2 问 AI（模式 B，当前默认）

```text
1. 用户在 /agents/ask 输入问题，点发送
2. 前端 lib/ask/use-ask-session.ts 组装请求
3. POST /api/b/ai/chat（或先创建会话再流式）
4. Next Route Handler 校验登录与配额
5. 调用 DeepSeek / 百炼 API（stream: true）
6. SSE 逐 token 推回浏览器
7. 前端 MarkdownContent 渲染；refs 事件展示引用卡片
8. （已登录）会话写入 SQLite，侧栏 history 可列出
```

**A 协议 SSE 事件顺序**（与类型 `types/ai-search.ts` 对齐）：

```text
meta → refs? → delta（多次）→ followups? → done | error
```

### 4.3 论文搜索（普通搜索）

```text
1. 首页 Alt+Enter 或 /search 页提交关键词
2. POST /api/v1/search/explore
3. Next 转发 → FastAPI → 外部 RETRIEVAL_API_URL
4. 返回 papers 列表，前端 paper-card 展示
5. FastAPI 不可用时回退本地 mock 数据
```

## 五、全栈知识点 ↔ 本项目对照表

| 概念 | 通用解释 | 在本项目中的例子 |
|------|----------|------------------|
| 组件 | UI 积木 | `ComposerShell`、`AskStage` |
| Hook | 复用状态与副作用 | `useAskSession()` |
| REST API | 用 URL + 方法操作资源 | `/api/b/sessions` CRUD |
| 流式响应 | 边生成边返回 | AI 对话 SSE |
| ORM | 用代码操作数据库 | Prisma（B 模块）、Better Auth 用 PG |
| 中间层代理 | 同源转发隐藏后端 | `app/api/v1/[...path]/route.ts` |
| 契约 / Schema | 字段约定 | `CreateChatSessionRequest` |
| Feature 目录 | 按业务分模块 | `features/agents/` |
| 环境隔离 | dev / prod 不同配置 | `.env.local` 不提交 Git |

## 六、本地跑通项目（阶段一必做）

### 6.1 Web 前端

```bash
cd apps/web
pnpm install
cp .env.example .env.local   # 按需填写 DATABASE_URL、DEEPSEEK_API_KEY 等
pnpm dev                     # 默认 http://localhost:3000
pnpm typecheck               # 类型检查
```

### 6.2 FastAPI 后端（论文检索 / 模式 A 联调）

```bash
cd apps/backend
uv sync
uv run uvicorn app.main:app --reload --port 8000
```

Web 侧 `.env.local` 增加（仅服务端）：

```env
BUSINESS_BACKEND_URL=http://127.0.0.1:8000
```

### 6.3 建议的自测清单

- [ ] 首页能打开，Composer 能切换「搜索 / 问 AI」  
- [ ] 能注册/登录（需配好 `DATABASE_URL`）  
- [ ] `/agents/ask` 能发出问题并看到流式回复（需 `DEEPSEEK_API_KEY`）  
- [ ] Alt+Enter 或搜索页能出论文结果（需 FastAPI + 检索服务）  
- [ ] `pnpm typecheck` 无报错

## 七、Git 与协作规范

### 7.1 分支流程

```text
dev  →  新建 feat/xxx  →  开发  →  自测  →  合并回 dev
```

不要在 `dev` 上长期直接堆提交（与飞书文档一致）。

### 7.2 阶段二的任务流程（修融合问题时）

```text
确定问题 → 写修改方案 → 列出将改的文件 → 负责人确认 → 开发 → 自测 → 汇报
```

跨模块改动（公共组件、数据库 Schema、公共 API）**先在群里同步**，不要悄悄改别人模块。

### 7.3 禁止重复建设（非常重要）

动手前问：**项目里是不是已经有了？**

禁止再建：

- 第二套 Auth  
- 第二套数据库访问  
- 第二套 Backend Client  
- 重复的公共组件（Composer、session client、types 等）  
- 与现有架构平行的新目录  

公共能力应上提到 `lib/`、`types/`，而不是在 `modules/ai-agent-b/` 再 copy 一份。

## 八、阶段一自测：你能回答这三问吗？

飞书文档里的「阶段一简单验收」：

1. **当前项目前后端怎么分工？**  
   → Next.js 负责页面 + BFF + Auth；FastAPI 负责业务 API（检索、目标态 AI）；外部服务负责大模型与论文库。

2. **一次 Chat 从页面到后端怎么走？**  
   → Feature 组件 → `useAskSession` → `/api/b` 或 `/api/v1` →（A 模式）FastAPI → LLM；SSE 流回页面渲染。

3. **以后改功能该动哪些目录？**  
   → 页面 UI：`features/`；接口封装：`lib/api/`；类型：`types/`；Python 业务：`apps/backend/`；Auth：`lib/auth/`（勿动第二套）。

## 十、阶段二预告：你很快会碰到的「融合问题」

读架构时可以先有印象，具体实现等阶段二任务：

| 方向 | 问题 | 目标 |
|------|------|------|
| Auth ↔ Chat | 登录身份如何传到 Chat | 统一用 Better Auth + `X-Shenzhi-User-Id` |

| Search 边界 | 论文搜索 / 联网 / Deep Search | 理清职责，去重复 |

## 十一、常见误区

| 误区 | 正确理解 |
|------|----------|
| 「后端就是 FastAPI」 | 当前 AI 主力仍在 Next `/api/b`；FastAPI 是目标态 + 论文检索 |
| 「浏览器直连 FastAPI 更快」 | 违反架构；Cookie 与密钥不能暴露 |
| 「在 B 模块 copy 一个 Composer 省事」 | 造成双栈，后续无法合并 |
| 「types 改一处就行」 | 必须只维护 `types/ai-search.ts`，B 模块只 re-export |
| 「dev 上改完就 push 主分支」 | 应走 `feat/*` 分支，合并前自测 |
